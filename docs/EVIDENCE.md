## 0. 测试机硬件 / Test Rig

| 项目 | 实测值 |
|---|---|
| GPU | NVIDIA RTX 3060 **Laptop**，**12288 MiB** VRAM，compute capability **sm_86** |
| 驱动 | **616.92**（笔记本 OEM 驱动；INF `oem14.inf` 中**无任何 Pascal 设备 ID**） |
| CPU | Intel **i5-9400F**（6 核 6 线程，**无核显**） |
| 内存 | **15.94 GiB** DDR4-2666，**2/2 插槽已满**（2×8 GB Samsung）→ 无法扩容 |
| 主板 | ASUS **B365M-PIXIU**（mATX，**1× PCIe 3.0 x16** + 2× x1，**无 x4 槽**） |
| 系统盘 | C: SSD **237 GB** |
| 数据盘 | D: HDD **466 GB** |

> 结论（**仅针对本测试机**，不是普遍规律）：这台机器的扩展空间几乎被堵死——
> 内存 2/2 插槽已满，要加内存只能**整组替换**而非加装；显卡为笔记本 dGPU，
> 且 OEM 驱动 INF 中无 Pascal 设备 ID；主板只有 1 条 x4 以上 PCIe 槽，
> 无法叠加第二块卡。因此本项目的优化都必须在"12 GB VRAM + 16 GB RAM"这个**边界**内完成。
> 换一台有 4 条内存插槽或 2 条 x16 槽的台式机，结论可能不同。

| 文件 | 字节数 | 说明 |

| `mmproj-F16.gguf` | **927,607,488** | 视觉投影器（`projector_type=qwen3vl_merger`） |
| Qwen-Image 2.1 **DiT** | **7,256,787,829**（6.76 GiB） | diffusion 主体 |

四个主要权重合计 **32,641,308,901 B ≈ 30.40 GiB**；含投影器 **≈ 31.26 GiB**。

> 重要口径提醒：**以上全部是"文件体积"，不是运行时显存占用。**
> 例如文本编码器权重 8.71 GiB，但编码器阶段的**实际总显存占用更高**（估算约 9.4–10.3 GiB，见 `OOM_MITIGATION.md`）。
> README 中任何标为"实测"的显存数字，都指进程/设备的实际占用；标为"体积/权重"的，指上表这类字节数换算。


模型元数据（读取自 GGUF header）：

```
general.architecture      = qwen35
block_count               = 65
full_attention_interval   = 4        → 约 16 层全注意力，其余为 SSM/线性层
ssm.state_size            = 128
ssm.inner_size            = 6144
embedding_length          = 5120
context_length            = 262144
nextn_predict_layers      = 1
```

> 关键点：这是 **hybrid attention**（混合注意力）架构，不是纯 Transformer。
> 65 层里只有约 16 层持有随上下文线性增长的 KV cache，这是 16 GB 内存能撑住 64K 上下文的**根本原因**。
> 如果是同尺寸纯注意力模型，64K KV cache 本身就要吃掉十几 GB。

## 2. 显存/内存分层：为什么用 `-ngl` 而不是 `-ncffn`

同样把 27B 塞进 12 GB 显存，两种做法的实测差异：

**测量阶段 / Measurement stage**（这一列必读：不同阶段的读数不可互相比较 / the stage column is mandatory reading: readings from different stages are not comparable）：

| 配置 | 测量阶段 / Stage | VRAM | 物理内存占用 / RAM | 关键机制 |
|---|---|---|---:|---|
| `-ngl 44`（纯按层切分） | **运行期**运行推理 / run time | 11,552 MiB | **96.1 %** | CPU 侧张量保留为**可回收的 mmap 文件页**，内存吃紧时可被驱逐 |
| 100K 上下文 / `-ngl 42` | **运行期** / run time | 11,814 MiB | **99.0 %** | 同上，但上下文更大 |
| `-ngl 48` | — | — | — | **OOM**。该次运行的上下文长度**未记录**，不要假定等于 64K 或 100K。 |
| `-ncffn` 张量覆盖 | **运行期** / run time | — | **99.3 %**，另有 13.4 GB 进程**私有提交内存** | 把张量**拷贝**进匿名私有内存，不可驱逐 |

> **这是本项目最重要的一条实测发现**：`-ncffn` 看起来更精细地把 FFN 放 CPU，
> 但它实际做的是**拷贝**，生成匿名私有页，操作系统无法回收；
> 而 `-ngl` 的部分卸载让 CPU 侧张量停留在 mmap 映射的文件页上，**可以被页回收器驱逐**。
>
> **量级要说清楚 / Say the magnitude honestly.** 99.3 % 降到 96.1 % 的差别是
> **3.2 个百分点**，不是内存压力被消除了。两个配置**都远高于**本项目自设的 90 % 安全线。
> 它真正改变的是这些页**能否被回收**，而不是占用了多少。
> 另外 13.4 GB 是进程的**私有提交内存（private committed memory）**，不是"从物理内存里省出的 13.4 GB"，
> 这两个量不能混为一谈。
>
> The 99.3 % to 96.1 % change is **3.2 percentage points**, not the elimination of memory pressure;
> both configurations sit well above this project's own 90 % safety line. What it changes is
> *whether those pages can be reclaimed*, not how much is occupied. The 13.4 GB figure is the
> process's **private committed memory**, not "13.4 GB of physical RAM saved" - different quantities.

### 页锁定（mlock）的代价

| 配置 | 测量阶段 / Stage | 物理内存占用 / RAM | 空闲 / Free |
|---|---|---|---:|
| `-lm mmap+mlock` | 加载/待机 / load & standby | 94.2 % | **0.93 GiB** ← 几乎窒息 |
| `-lm mmap`（本项目默认） | 加载/待机 / load & standby | **29.7 %** | 宽裕 |

> **不要把这张表的 29.7 % 和上表的 96.1 % 放在一起比较。**
> 上表是**推理运行期**读数，这张表是**加载/待机**阶段读数；工作负载不同，
> 差异主要来自阶段差异，而不是 mlock 与 mmap 的差异本身。
> 同一个 mmap 配置在运行期的读数就是上表的 96.1 %。
>
> **Do not compare the 29.7 % here with the 96.1 % above.** The first table is measured **during
> inference**, this one at **load/standby**. Different workloads - the gap is mostly the stage
> difference, not the mlock-versus-mmap difference. The same mmap configuration reads 96.1 % at run time.
>
> `mlock` 把模型页钉死在物理内存里，对 15 GB 模型来说等于把整机内存锁死。本项目**明确不使用 mlock**。

## 3. 上下文长度：为什么定在 64K

需求方要求 100K，但实测 100K 时 RAM 冲到 **99.0 %**，系统进入持续换页，交互体验崩塌。

| 上下文 | `-ngl` | VRAM | RAM | 判定 |
|---|---|---|---|---|
| 64,000 | 44 | 11,552 MiB | 96.1 % | **采用**：可稳定交互 |
| 100,000 | 42 | 11,814 MiB | 99.0 % | 否决：换页严重 |
| — | 48 | OOM | — | 否决 |

> 96 % 的 RAM 占用**不满足**"≥90 % 才算安全"的内部验收规则。
> 但这是**硬件算术**的结果，不是配置问题：15.36 GB 模型 + 64K KV cache 在 16 GB 物理内存上的必然结论。
> 实际运行时这些占用大部分是**可驱逐的 mmap 页**，所以系统不会死，只是留给其他程序的空间很小。
> 本项目因此在启动脚本里加了 **6144 MB 空闲内存闸门**：低于此值拒绝启动，避免把机器拖死。

### 提交上限（Commit Limit）

为让 15.36 GB 模型在 16 GB 内存上完成加载，需要把页面文件调大：

| 项目 | 调整前 | 调整后 |
|---|---|---|
| 页面文件 | 8,107 MB | **32,768 MB**（C: 固定大小） |
| 提交上限 | — | **47.94 GiB** |
| 剩余余量 | — | **39.39 GiB** |

脚本：`tools/set-pagefile.ps1`（需管理员/UAC）。

## 4. KV cache 量化

```
-ctk q4_0 -ctv q4_0 -fa on
```

- KV 量化**必须**同时开启 `-fa on`（flash attention），否则 llama.cpp 会拒绝或静默回退。
- `-ub 256`（micro-batch）缩小计算缓冲区，为 64K 上下文再挤出显存。

## 5. 速度实测 / Throughput

| 项目 | 实测值 | 备注 |
|---|---|---|
| LLM 生成 | **约 4.0 tok/s** | 64K 配置、SSD 热态 |
| 1080p 出图 | **约 88 秒** | 1920×1088 |
| 2K 出图 | **约 4.5 分钟** | 2560×1440 |
| **模型切换（重新加载）** | **数十秒** | SSD 热态；每次流水线都要付一次 |

> 4 tok/s 是"可用但慢"——足够写提示词、写脚本、做长文分析；
> 不适合实时对话式高频交互。这是 12 GB 显存下 27B 模型的物理上限，
> 不是软件调优能突破的。
>
> **上表三项（生成/1080p/2K）都不含模型切换开销。**
> "提交任务 → 拿到图"的真实墙钟时间 = 提示词生成 + 切换加载 + 出图，
> 因此明显长于 88 秒或 4.5 分钟这两个单项数字。

## 6. 串行加载（Serial Loading）为什么是必需的

两个模型**不能同时驻留**：

- Qwen3.8-27B 单模型就要 11,552 MiB / 12,288 MiB 显存（94 %）
- ComfyUI + Qwen-Image 2.1（diffusion + text encoder + VAE）需要另外数 GB

因此总控台的流程是**严格串行**的：

```
start llama → 生成提示词 → stop llama → start ComfyUI → 出图 → stop ComfyUI → start llama
```

每次切换都要付出模型重新加载的时间（SSD 热态下几十秒），这是 12 GB 显存的**必然代价**。

## 7. 离线验证方法

本项目的主张是：**部署完成后完全本地推理，不需要任何云端 API**（首次获取权重与运行时仍需联网）。

验证方法（这是一个**可复现的流程**，不是"已完成的测试报告"——仓库里没有附带日期的运行结果）：

1. 用 `tools/fw-on.ps1` 给**两个实际执行推理的程序**加上 Windows 防火墙**出站阻断**规则
   （ComfyUI 的嵌入式 `python.exe` 与 `llama-server.exe`）
2. 照常跑完整流程（提示词生成 + 出图）
3. 用 `tools/fw-off.ps1` 删除规则并回读确认

> **适用范围要说清楚**：规则是**按程序**生效的，只覆盖上述两个可执行文件，
> **不是**"阻断全机所有出站流量"，也没有关闭防火墙；Node.js 总控台本身不在阻断范围内。
> 另需注意：回环地址（127.0.0.1）本身不经过 Windows 防火墙的出站过滤，
> 所以总控台 ↔ llama-server ↔ ComfyUI 之间的本地通信始终正常。
> 因此这条流程能证明的是："**推理路径不依赖对外网络**"，而不是"整机完全断网仍可运行"。

## 9. 开发期观测记录（单项观测，非基准）

下面两条是**开发过程中记录的单次观测**，不是系统性基准，也没有原始日志文件留存。
在此列出，是为了让 README 里对应的叙述可追溯到一个明确来源，而不是悬空的断言。

**9.1 Token 预算被思考链吃掉的观测。** 在一次出图任务的提示词生成调用中，观测到
思考链与正式回答合计消耗 **415 / 420** 个 token，其中推理内容 **704** 字符、回答 **1302** 字符。
最终修复是把 `max_tokens` 从 420 提高到 **2000**，并把默认思考档位设为 `off`。

> 需要区分两件事：这一次观测到的是**回答被压缩到接近最小**；
> 而"返回空内容"的故障是同一根因下的另一个表现。两者都由"思考链与回答共享同一 token 预算"引起，
> 但上表数字只对应前者那一次调用。

**9.2 独立 SHA-256 校验。** `place_models.ps1` 只比对字节数，因此本次部署另做了一次独立的
SHA-256 比对，3 个模型文件**全部一致**。

> 说明：这次比对的结果**只记录在本文档中**，没有单独持久化为哈希报告文件；
> 期望哈希值见 `archive/PLAN_v3.md`，但那是计划值，不是本次的运行输出。

## 10. 完整性校验与发布者身份（两件不同的事）

本仓库的下载与校验脚本能证明的是**文件是否完整**，不能证明**文件是谁发布的**：

| 校验手段 | 能证明 | 不能证明 |
|---|---|---|
| 字节数比对 | 长度符合预期 | 内容未被替换 |
| SHA-256 比对（若上游提供） | 内容与已知哈希一致 | **该哈希本身可信**（除非来自独立可信渠道） |
| ZIP 能打开 / CRC / 条目数 | 归档结构完整、未截断 | 发布者身份、是否被恶意替换 |
| 解压后能运行 | 至少不是明显损坏 | 不含后门或恶意代码 |

> 因此：`fetch_comfy.ps1` / `post_download.ps1` 会下载并**执行**第三方内容。
> 在运行之前，请自行确认来源，并在有条件时用**独立已知**的哈希或签名核对。
> 本项目不声称提供任何发布者身份验证能力。
>
> 另外，`post_download.ps1` 在解压后执行的 Python 来自下载得到的 ComfyUI 本体——
> 这是使用 ComfyUI 的固有前提，但也意味着你在运行前应当知道自己在执行什么。

## 11. 边界与已知限制 / Limits

明确列出，避免过度承诺：

1. **RAM 占用 96 %**，不满足 90 % 安全线。这是本机配置下的实测结果；在 16 GB 物理内存上属于硬件算术，本仓库没有找到"保持 64K 上下文同时把它降下来"的配置。
2. **≈4 tok/s**，慢。这是**当前配置下的实测吞吐**；本仓库没有做跨配置对比，因此不宣称它是不可突破的上限。
3. **两个模型不能共存**，必须串行切换，每次切换需要重新加载，SSD 热态下数十秒。
4. **参考图模式的输出跟随参考图长宽比**：喂方形参考图会得到 1920×1920 方形输出，不会自动裁成 16:9。
5. **安全对齐无法移除**：Qwen3.8 的安全对齐训练在权重里，不存在可以单独关闭的模块
   （实测 chat template 全长 9,993 字符，安全检查关键词数量为 **0**；本机也没有 guard/moderation 模型）。
   本项目的缓解手段只有系统提示词层面的"减少过度拒答"文本，**不是**真正的对齐移除。
6. **驱动限制**：笔记本 OEM 驱动 `oem14.inf` 不含 Pascal 设备 ID，本机无法用 Pascal 卡（如 P40/P100）扩容显存。
7. **无第二条 x4 以上 PCIe 槽**，无法加装第二块显卡做显存叠加。
